## Résumé exécutif

✅ RLS est **activé sur les 53 tables** — aucune table entièrement non protégée.  
❌ Mais la quasi-totalité des policies sont `qual = true` sans condition → **accès anon total**, ce qui revient à ne pas avoir de RLS utile sur ces tables.  
⚠️ **Une seule table** a un vrai filtre row-level : `objectifs_energie` (filtrée par `user_sites`).

Le problème fondamental : la clé `anon` est exposée dans le JavaScript front (dashboard.html, rapport.html, etc.). Toute personne qui inspecte le code source peut faire des requêtes directes à l'API Supabase avec cette clé et accéder à **toutes les données de tous les clients**.

## Points critiques à corriger en priorité

### 1. `sessions` — URGENT
Policy `allow_all` (public, ALL, qual=true) permet à n'importe qui de lire tous les tokens de session. Si ces tokens servent à authentifier les techniciens, c'est une faille d'usurpation d'identité.

**SQL à soumettre dans Supabase :**
```sql
-- Supprimer la policy permissive
DROP POLICY IF EXISTS "allow_all" ON sessions;

-- Remplacer par : un technicien ne voit que sa propre session
CREATE POLICY "sessions_own" ON sessions
  FOR ALL TO anon, authenticated
  USING (token = current_setting('request.headers', true)::json->>'x-session-token' OR auth.uid() IS NOT NULL);
```
*(à adapter selon comment le token est vérifié dans ton flow)*

---

### 2. `tokens` — SELECT ouvert
La policy `tokens_read` (public SELECT, qual=true) expose tous les tokens à qui connaît la clé anon.

**SQL à soumettre :**
```sql
DROP POLICY IF EXISTS "tokens_read" ON tokens;
-- Si les tokens sont lus par un flow bot uniquement, ne laisser que service role
```

---

### 3. `signalements`, `maintenances`, `sites`, `prestataires` — Isolation client
Ces tables sont entièrement accessibles cross-clients. Un client A peut lire les données du client B.

**Solution propre :** filtrer par `groupe_id` ou `site_id` via la table `user_sites`. Exemple pour `signalements` :
```sql
DROP POLICY IF EXISTS "allow all" ON signalements;
DROP POLICY IF EXISTS "anon_insert_signalements" ON signalements;
DROP POLICY IF EXISTS "anon_update_signalements" ON signalements;

-- Lecture : filtré par sites autorisés (pour dashboard authentifié)
-- INSERT/UPDATE anon : autorisé sans restriction (nécessaire pour le bot WhatsApp)
CREATE POLICY "signalements_read_authenticated" ON signalements
  FOR SELECT TO authenticated
  USING (groupe_id IN (SELECT site_id FROM user_sites WHERE user_id = auth.uid()));

CREATE POLICY "signalements_anon_insert" ON signalements
  FOR INSERT TO anon WITH CHECK (true);

CREATE POLICY "signalements_anon_update" ON signalements
  FOR UPDATE TO anon USING (true);
```

---

### 4. `contacts` — Écriture ouverte à anon
La policy `contacts_write` (public, ALL, qual=true) permet à n'importe qui de créer, modifier ou supprimer des contacts.

```sql
DROP POLICY IF EXISTS "contacts_write" ON contacts;
CREATE POLICY "contacts_write_authenticated" ON contacts
  FOR ALL TO authenticated USING (true) WITH CHECK (true);
```

## Note sur l'architecture actuelle

L'application utilise la clé `anon` directement dans le JS front, ce qui est une pratique Supabase commune pour les apps sans auth. Le vrai verrou est donc les RLS policies — mais actuellement elles ne filtrent pas.

La solution long terme est de migrer vers **Supabase Auth** (JWT par utilisateur) pour que chaque session ait un `auth.uid()` et que les policies filtrent par cet identifiant. C'est un chantier mais c'est l'architecture cible.

À court terme, les corrections prioritaires (points 1-4 ci-dessus) peuvent être appliquées sans toucher au code front.
